Java Gradle

O Gradle faz o mesmo trabalho que o Maven: baixa as bibliotecas, compila, roda os testes e empacota. A diferença está na receita: em vez de um XML, você escreve um pequeno programa em Kotlin, o build.gradle.kts. É a ferramenta padrão dos aplicativos Android e muito usada em projetos Java novos.

Você vai aprender
  • Criar um projeto com gradle init, sem perguntas.
  • O que é cada arquivo gerado, e o build.gradle.kts linha por linha.
  • O que é o wrapper (./gradlew) e por que usá-lo.
  • ./gradlew build, run e test, com as saídas reais (e uma falha).
  • Adicionar uma dependência e o que acontece quando ela não existe.
  • O que é o daemon do Gradle.
  • Quando escolher Maven ou Gradle.

Esta aula supõe que você já leu a de Maven: as ideias de dependência, repositório e estrutura src/main/java são as mesmas. Os exemplos rodam na máquina fictícia da Ana, com Gradle 9.8.1 e JDK 25.

A ideia: a mesma cozinha, outra receita

Se o Maven é uma cozinha padronizada com uma receita em formulário (você preenche os campos do pom.xml), o Gradle é a mesma cozinha, mas a receita é escrita como um roteiro: dá para pôr "se", "repita", criar tarefas novas. Para projetos simples, as duas receitas têm quase o mesmo tamanho. Para projetos enormes e cheios de particularidades, o roteiro do Gradle é mais flexível.

O Gradle trabalha com tarefas (tasks): compileJava, test, jar, build… Cada tarefa depende de outras, e o Gradle roda só as que precisam (se nada mudou, ele pula).

3. A receita: build.gradle.kts

O arquivo gerado tem comentários em inglês explicando cada bloco. Sem os comentários, e depois de duas mudanças da Ana (ela tirou a biblioteca de exemplo Guava, que o modelo inclui, e acrescentou a Gson, que você vai ver adiante), ficou assim:

plugins {
    application
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation(libs.junit.jupiter)
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
    implementation("com.google.code.gson:gson:2.13.1")
}

    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }

    mainClass = "br.com.ana.mercado.App"

    useJUnitPlatform()

TrechoO que faz
plugins { application }Liga o plugin application: compilar Java, criar o JAR e, além disso, a tarefa run e scripts para executar o programa.
repositories { mavenCentral() }Onde buscar bibliotecas: no mesmo Maven Central que o Maven usa.
dependencies { … }As bibliotecas. A palavra antes dos parênteses diz para que serve cada uma:
  implementation("grupo:nome:versão")Usada pelo programa (como a dependência sem scope do Maven). As coordenadas vão numa linha só, separadas por :.
  testImplementation(libs.junit.jupiter)Usada só nos testes (como <scope>test</scope>). libs.junit.jupiter aponta para o catálogo libs.versions.toml, que diz org.junit.jupiter:junit-jupiter, versão 6.0.1.
  testRuntimeOnly(…)Necessária só para rodar os testes (o "lançador" do JUnit).
java { toolchain { languageVersion = … 25 } }Compilar e rodar com um JDK 25. O Gradle procura um JDK 25 instalado (e, se não achar, pode baixar um, graças ao plugin foojay-resolver declarado no settings.gradle.kts).
application { mainClass = "…" }A classe principal, para o ./gradlew run.
tasks.named<Test>("test") { useJUnitPlatform() }Configura a tarefa test para usar o JUnit 5/6 (a "plataforma JUnit").

Compare com o pom.xml: a dependência da Gson, que no Maven ocupa 5 linhas de XML, aqui é uma linha. Como o arquivo é código Kotlin, o editor (como o IntelliJ) completa e confere enquanto você digita.

A classe gerada, App.java, tem um método que devolve a saudação, e um teste para ele. A Ana trocou o texto para português:

package br.com.ana.mercado;

public class App {
    public String getGreeting() {
        return "Bem-vinda ao mercado da Ana!";
    }

    public static void main(String[] args) {
        System.out.println(new App().getGreeting());
    }
}

Missão: o teste do projeto confere se getGreeting() devolve exatamente Bem-vinda ao mercado da Ana!. O main abaixo imita esse teste e mostra PASSED ou FAILED. O método está com um erro de digitação: conserte-o (sem mexer no main) até aparecer PASSED.

public class Main {
    public String getGreeting() {
        return "Bem-vindo ao mercado da Ana!";
    }

    public static void main(String[] args) {
        String esperado = "Bem-vinda ao mercado da Ana!";
        String obtido = new Main().getGreeting();
        if (esperado.equals(obtido)) {
            System.out.println("PASSED");
        } else {
            System.out.println("FAILED: expected: <" + esperado + "> but was: <" + obtido + ">");
        }
    }
}

4. O wrapper: ./gradlew

O gradle init criou um script chamado gradlew (Gradle wrapper, "embrulho do Gradle"). Ele é um pequeno programa que baixa a versão certa do Gradle para este projeto e a usa. A versão está anotada em gradle/wrapper/gradle-wrapper.properties:

$ cat gradle/wrapper/gradle-wrapper.properties
distributionBase=GRADLE_USER_HOME
distributionPath=wrapper/dists
distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.1-bin.zip
networkTimeout=10000
retries=0
retryBackOffMs=500
validateDistributionUrl=true
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists

A linha que importa é distributionUrl: "este projeto usa o Gradle 9.8.1, baixado deste endereço". Por que isso é bom? Porque o Gradle muda bastante entre versões. Com o wrapper, quem baixar o seu projeto (um colega, o servidor que gera as versões) roda ./gradlew build e usa exatamente o mesmo Gradle, mesmo sem ter nenhum Gradle instalado. Por isso a regra é: use sempre ./gradlew num projeto que tem wrapper, e guarde os arquivos do wrapper junto com o código (no Git).

O daemon

Iniciar uma JVM e carregar o Gradle leva vários segundos. Para não pagar isso a cada comando, o Gradle deixa um processo rodando em segundo plano, o daemon (palavra antiga da informática para "processo que trabalha nos bastidores"). Os comandos seguintes conversam com ele e ficam bem mais rápidos. Ele se desliga sozinho depois de um tempo parado, ou com:

$ ./gradlew --stop
Stopping Daemon(s)
1 Daemon stopped

A mensagem Starting a Gradle Daemon, 2 stopped Daemons could not be reused só quer dizer que havia daemons parados (a Ana parou o daemon depois de cada exemplo) e um novo foi iniciado. O daemon ocupa memória; num computador modesto, vale parar quando terminar de trabalhar.

import java.util.List;

public class Main {
    record Item(String nome, double preco) {}

    public static void main(String[] args) {

Qual usar? Num projeto que já existe, a que ele usa. Num projeto novo seu, qualquer uma serve; se a equipe ou o tutorial que você segue usa uma, fique com ela. As duas usam o mesmo Maven Central, a mesma estrutura src/main/java e o mesmo JUnit, então mudar de uma para outra é tranquilo.

O que aconteceu: a versão 2.99.0 não existe. A primeira frase (sobre configuration cache) assusta, mas é consequência; a causa está mais abaixo: Could not find …, com o endereço onde o Gradle procurou. Como resolver: corrija as coordenadas (procure em central.sonatype.com).

bash: ./gradlew: Permissão negada 
$ ./gradlew build
bash: ./gradlew: Permissão negada

O que aconteceu: o script perdeu a permissão de execução (acontece ao copiar o projeto de um zip ou do Windows). Como resolver: chmod +x gradlew. Para rodar uma vez sem mudar a permissão: sh gradlew build.

Directory '/home/ana' does not contain a Gradle build. 
$ gradle build

A Gradle build's root directory should contain one of the possible settings files: settings.gradle, settings.gradle.kts, settings.gradle.dcl. It may also contain one of the possible build files: build.gradle, build.gradle.kts, build.gradle.dcl.

To create a new Gradle build in this directory run 'gradle init'

BUILD FAILED in 2s

O que aconteceu: você está fora da pasta do projeto. Como resolver: cd para a pasta que tem o settings.gradle.kts (a raiz, não a app).

There were failing tests

O que aconteceu: pelo menos um teste falhou, e o Gradle para o build (não gera o JAR). Como resolver: veja o motivo no relatório app/build/reports/tests/test/index.html ou ligue o testLogging com exceptionFormat = FULL, como na seção 6. Depois corrija o código (ou o teste, se o teste estiver errado).

Resumo

  • O Gradle faz o mesmo que o Maven (dependências e build), com a receita em código: build.gradle.kts.
  • gradle init --type java-application --dsl kotlin … cria o projeto; o código fica em app/src/main/java.
  • Dependências: implementation("grupo:nome:versão"); só para testes: testImplementation(…).
  • Use sempre o wrapper ./gradlew: ele baixa e usa a versão certa do Gradle.
  • ./gradlew build, run, test, clean; o gerado vai para app/build/.
  • UP-TO-DATE = tarefa pulada porque nada mudou. O daemon deixa os comandos seguintes rápidos; --stop o desliga.
  • Num BUILD FAILED, procure a causa em What went wrong e nas linhas do javac ou do teste.
