Projeto: Sistema de Biblioteca

Este é o projeto de orientação a objetos do guia. Em vez de um programa com um main enorme, você vai construir várias classes pequenas, cada uma responsável por uma coisa: o livro sabe se está disponível, o usuário sabe quantos livros pode levar, a biblioteca guarda tudo e aplica as regras. Quando alguma regra é quebrada, uma exceção com nome próprio avisa o que aconteceu.

Você vai praticar
  • Classes e objetos, construtores e encapsulamento (atributos private, métodos que protegem as regras).
  • Interfaces implementadas por records, e polimorfismo.
  • HashMap para achar um livro pelo código.
  • Records como "fichas" de dados (Emprestimo).
  • Criar suas exceções, com herança entre elas, e throw e throws.
  • Um programa com vários arquivos.

O que vamos construir

No fim, a pasta do projeto terá dez arquivos, um por classe, e o Main encena um dia na biblioteca: o Bruno (aluno) e a Carla (professora) tentam pegar livros, e as regras entram em ação.

Antes de começar

Este projeto pede o Nível 2 quase inteiro: classes, encapsulamento, interfaces, records e exceções, além de HashMap. No seu computador, cada classe pública vai num arquivo com o mesmo nome:

$ mkdir -p java/biblioteca
$ cd java/biblioteca
No editor do guia, tudo num arquivo só

Para as missões caberem numa caixa, as classes estão juntas num único Main.java, uma depois da outra. O Java permite isso, com uma regra: só a classe Main pode ser public; as outras ficam sem o public na frente de class, interface ou record. O comportamento é o mesmo. No seu computador, prefira um arquivo por classe, como nas listagens desta página.

Etapa 1 · O livro

Começamos pela peça mais simples. Um livro tem código, título, autor e uma situação: disponível ou emprestado. A regra de ouro do encapsulamento: ninguém de fora mexe direto nos dados do livro. Os atributos são private, e quem quiser mudar a situação tem que pedir ao livro, pelos métodos emprestar() e devolver().

public class Livro {
    private final String codigo;
    private final String titulo;
    private final String autor;
    private boolean disponivel;

    public Livro(String codigo, String titulo, String autor) {
        this.codigo = codigo;
        this.titulo = titulo;
        this.autor = autor;
        this.disponivel = true;
    }

    public String getCodigo() {
        return codigo;
    }

    public String getTitulo() {
        return titulo;
    }

    public String getAutor() {
        return autor;
    }

    public boolean isDisponivel() {
        return disponivel;
    }

    public void emprestar() {
        disponivel = false;
    }

    public void devolver() {
        disponivel = true;
    }

    @Override
    public String toString() {
        String situacao = disponivel ? "disponível" : "emprestado";
        return codigo + " | " + titulo + " | " + autor + " | " + situacao;
    }
}
ParteO que é
private final String codigo;Atributo privado (só a própria classe enxerga) e final (definido uma vez, no construtor, e nunca mais muda). Código, título e autor de um livro não mudam.
private boolean disponivel;Privado, mas não final: muda a cada empréstimo, só que apenas pelos métodos da classe.
public Livro(…)O construtor. this.codigo = codigo copia o parâmetro para o atributo (this). Todo livro nasce disponível.
getCodigo(), isDisponivel()Os getters: deixam ler sem deixar mudar. Para boolean, o costume é isAlgo() em vez de getAlgo().
Não há setDisponivel(…)De propósito. Na etapa 5, emprestar() vai recusar um livro já emprestado; com um setter, qualquer um passaria por cima dessa regra.
@Override public String toString()Diz como o livro vira texto no println (sobrescrita). O ? : é o operador ternário.

Etapa 2 · Os usuários

A biblioteca tem dois tipos de usuário: alunos, que levam até 2 livros, e professores, que levam até 5. Os dois têm nome e um limite, mas o limite é diferente. Isso pede uma interface: um "contrato" que diz o que todo usuário sabe responder, deixando cada tipo decidir como.

public interface Usuario {
    String nome();

    int limiteDeLivros();
}

Cada tipo de usuário é um record que implementa a interface:

public record Aluno(String nome) implements Usuario {
    @Override
    public int limiteDeLivros() {
        return 2;
    }
}

public record Professor(String nome) implements Usuario {
    @Override
    public int limiteDeLivros() {
        return 5;
    }
}
public interface Usuario
O contrato: todo Usuario tem os métodos nome() e limiteDeLivros(). Uma interface só declara; não tem o corpo dos métodos.
record Aluno(String nome)
Um record com um componente, nome. O record já ganha o método nome(), que é exatamente o que a interface pede.
implements Usuario
"Cumpre o contrato Usuario." Se faltar um método da interface, o código não compila.
@Override public int limiteDeLivros()
O método que faltava. @Override avisa ao compilador que este método vem da interface; os métodos de interface são sempre public.
import java.util.List;

public class Main {
    public static void main(String[] args) {
        Usuario bruno = new Aluno("Bruno");
        Usuario carla = new Professor("Carla");

        List<Usuario> usuarios = List.of(bruno, carla);
        for (Usuario u : usuarios) {
            System.out.println(u.nome() + " pode levar até " + u.limiteDeLivros() + " livro(s). " + u);
        }
    }
}

$ java Main.java
Bruno pode levar até 2 livro(s). Aluno[nome=Bruno]
Carla pode levar até 5 livro(s). Professor[nome=Carla]

Aqui está o polimorfismo ("muitas formas"): as variáveis bruno e carla são do tipo Usuario, e o laço trata os dois do mesmo jeito. Mas u.limiteDeLivros() dá 2 para um e 5 para o outro, porque cada objeto responde do seu jeito. A biblioteca nunca vai precisar de um if (u é aluno). Se um dia surgir o tipo "Funcionário", basta criar um record novo; nada mais muda.

Quando dá errado: criar "um usuário qualquer"

Este código tem um erro de propósito.

$ java Main.java
Main.java:3: error: Usuario is abstract; cannot be instantiated
        Usuario alguem = new Usuario();
                         ^
1 error
error: compilation failed

"Usuario é abstrato; não pode ser instanciado." Uma interface é só o contrato, não dá para criar um objeto dela. Crie um Aluno ou um Professor e guarde numa variável do tipo Usuario.

E a herança com extends?

Daria para fazer com uma classe abstrata Usuario e as subclasses Aluno extends Usuario e Professor extends Usuario (veja Classes Abstratas). Escolhemos interface + records porque aqui os usuários só carregam dados e uma regra: não há código para herdar. A herança aparece na etapa 5, entre as exceções.

Etapa 3 · O acervo

Agora a classe que junta tudo: Biblioteca. Ela guarda os livros num HashMap, um "dicionário" em que cada chave (o código, "L1") leva a um valor (o livro). Achar um livro pelo código é instantâneo, sem percorrer lista nenhuma.

import java.util.HashMap;
import java.util.Map;

public class Biblioteca {
    private final Map<String, Livro> livros = new HashMap<>();

    public void cadastrar(Livro livro) {
        livros.put(livro.getCodigo(), livro);
    }

    public Livro buscar(String codigo) {
        Livro livro = livros.get(codigo);
        if (livro == null) {
            throw new IllegalArgumentException("Livro não encontrado: " + codigo);
        }
        return livro;
    }

    public void listarAcervo() {
        System.out.println("--- Acervo (" + livros.size() + " livros) ---");
        for (Livro livro : livros.values()) {
            System.out.println(livro);
        }
    }
}
TrechoO que faz
Map<String, Livro> livrosUm mapa com chave String e valor Livro. É private: só a biblioteca mexe no acervo.
livros.put(livro.getCodigo(), livro)Guarda o livro com o código como chave. Outro livro com o mesmo código substituiria o antigo.
livros.get(codigo)Devolve o livro daquela chave, ou null ("nada") se a chave não existe.
throw new IllegalArgumentException(…)Código inexistente é erro de quem chamou: avisamos na hora, com uma mensagem clara.
livros.values()Todos os livros do mapa, para o for-each.
public class Main {
    public static void main(String[] args) {
        Biblioteca bib = new Biblioteca();
        bib.cadastrar(new Livro("L1", "Dom Casmurro", "Machado de Assis"));
        bib.cadastrar(new Livro("L2", "Vidas Secas", "Graciliano Ramos"));
        bib.cadastrar(new Livro("L3", "O Cortiço", "Aluísio Azevedo"));
        bib.cadastrar(new Livro("L4", "Iracema", "José de Alencar"));

        bib.listarAcervo();
        System.out.println("Busca L2: " + bib.buscar("L2").getTitulo());
        System.out.println("Busca L9: " + bib.buscar("L9").getTitulo());
    }
}

A busca por L9 parou o programa, e isso é bom: a mensagem diz exatamente o que houve. Na etapa 5, o Main vai capturar esse erro.

O HashMap não promete ordem

Os livros apareceram em ordem (L1, L2, L3, L4) por coincidência das chaves curtas. Um HashMap guarda as chaves na ordem que for melhor para ele. Se a ordem importa, use um TreeMap (ordem das chaves) ou um LinkedHashMap (ordem de inserção); veja TreeMap e TreeSet.

Quando dá errado: esquecer de conferir o null

Se o buscar fosse só return livros.get(codigo);, o código L9 devolveria null, e o erro estouraria longe dali, no Main:

$ java Main.java
--- Acervo (4 livros) ---
L1 | Dom Casmurro | Machado de Assis | disponível
L2 | Vidas Secas | Graciliano Ramos | disponível
L3 | O Cortiço | Aluísio Azevedo | disponível
L4 | Iracema | José de Alencar | disponível
Busca L2: Vidas Secas

	at Main.main(Main.java:11)

"Não dá para chamar getTitulo() porque o valor devolvido por buscar é null." O Java até ajuda a achar a origem, mas a mensagem fala de null, não de "livro não encontrado". Conferir no lugar certo e lançar uma exceção com mensagem clara economiza horas de depuração.

Vamos dar nome a cada problema. Uma exceção própria é só uma classe que estende Exception. Criamos uma "mãe", BibliotecaException, e duas "filhas", uma para cada regra:

public class BibliotecaException extends Exception {
    public BibliotecaException(String mensagem) {
        super(mensagem);
    }
}

public class LivroIndisponivelException extends BibliotecaException {

extends BibliotecaException

Resumo

  • Cada classe tem uma responsabilidade: o Livro cuida da própria situação, a Biblioteca aplica as regras, o Main conversa com o mundo.
  • Atributos private + métodos com regras = encapsulamento; o compilador barra quem tenta pular.
  • Uma interface define o contrato; records podem implementá-la. Variáveis do tipo da interface dão polimorfismo.
  • HashMap acha pela chave; get devolve null quando não acha, então confira.
  • Exceções próprias dão nome aos problemas; herança entre elas permite tratar um grupo com um catch.
  • java Main.java compila sozinho as outras classes da pasta (Java 22+); javac *.java compila tudo.
