Java Testes com JUnit

Um teste automatizado é um pequeno programa que usa o seu programa e confere se o resultado está certo. Você escreve uma vez e roda quantas vezes quiser, em segundos. O JUnit é a biblioteca de testes mais usada em Java; nesta aula, a Ana vai testar a sua classe Conta com o JUnit 5 e o Maven.

Você vai aprender
  • Por que testar, e por que "testar à mão" não basta.
  • Pôr o JUnit 5 (Jupiter) num projeto Maven.
  • Escrever um teste com @Test e assertEquals.
  • Ler a saída do mvn test quando tudo passa e quando algo falha.
  • Testar exceções com assertThrows.
  • Preparar os testes com @BeforeEach e dar nomes legíveis com @DisplayName.
  • Rodar o mesmo teste com vários valores (testes parametrizados).
  • A ideia do TDD.

Você vai precisar de: classes e objetos, exceções e Maven. As anotações (as palavras com @) e as lambdas (() -> …) aparecem aqui só no uso básico.

Por que testar?

Pense numa cozinheira que, a cada mudança na receita do bolo, prova o bolo inteiro de novo: a massa, a cobertura, o recheio. Com uma receita, tudo bem. Com cem receitas, ela passaria o dia provando. Os testes automatizados são um provador que nunca cansa: você diz uma vez "com estes ingredientes, o resultado deve ser este", e ele confere tudo sempre que você pedir.

Até agora, para conferir um programa, você rodava o main e olhava a saída. Isso tem três problemas:

  1. Depende de você olhar com atenção. Um 150.0 que virou 50.0 passa despercebido no meio de 30 linhas.
  2. Não se repete sozinho. Você muda uma linha hoje e quebra algo que funcionava semana passada (isso tem nome: regressão). Ninguém reconfere tudo à mão a cada mudança.
  3. Não fica registrado. O que "deveria acontecer" está só na sua cabeça.

Um teste automatizado resolve os três: ele mesmo compara, roda com um comando e documenta o comportamento esperado em código.

A classe que vamos testar: a Conta da Ana

Um projeto Maven (~/banco), com a classe no lugar de sempre, src/main/java:

package br.com.ana.banco;

public class Conta {
    private final String titular;
    private double saldo;

    public Conta(String titular) {
        this.titular = titular;
    }

    public String getTitular() {
        return titular;
    }

    public double getSaldo() {
        return saldo;
    }

    public void depositar(double valor) {
        if (valor <= 0) {
            throw new IllegalArgumentException("Valor inválido: " + valor);
        }
        saldo += valor;
    }

    public void sacar(double valor) {
        if (valor <= 0) {
            throw new IllegalArgumentException("Valor inválido: " + valor);
        }
        if (valor > saldo) {
            throw new IllegalStateException("Saldo insuficiente");
        }
        saldo -= valor;
    }
}

Regras da conta: começa com saldo zero; depósito e saque precisam ser positivos; não dá para sacar mais do que o saldo. (Num banco de verdade, dinheiro seria BigDecimal; aqui usamos double com valores redondos para manter o foco nos testes.)

1. Pôr o JUnit no projeto

O JUnit é uma biblioteca como outra qualquer: entra no pom.xml como dependência. O pom.xml completo do projeto:

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>

            <version>5.13.4</version>

        </dependency>
    </dependencies>

org.junit.jupiter : junit-jupiter
O JUnit 5. Jupiter (o planeta Júpiter, porque é o "quinto") é o nome da parte que você usa para escrever testes. Este artefato traz tudo junto: as anotações, as verificações e o "motor" que executa os testes.
5.13.4
A versão. Em 2025 saiu o JUnit 6, com o mesmo Jupiter: o código desta aula funciona igual nele.
<scope>test</scope>
"Só para os testes": o JUnit é usado em src/test/java e não vai para o JAR do programa.

Quem executa os testes no Maven é o plugin Surefire ("à prova de falhas"), que já vem configurado: ele procura as classes de teste em src/test/java e roda todas na fase test.

2. O primeiro teste

Os testes ficam em src/test/java, no mesmo pacote da classe testada, numa classe com o mesmo nome mais Test:

package br.com.ana.banco;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class ContaTest {

    @Test
    void depositoAumentaOSaldo() {
        Conta conta = new Conta("Ana");
        conta.depositar(100.0);
        assertEquals(100.0, conta.getSaldo());
    }
}
import static …Assertions.assertEquals
Um import static traz um método estático de outra classe, para usar sem o nome dela: assertEquals(…) em vez de Assertions.assertEquals(…). Assertion = "afirmação", "verificação".
import org.junit.jupiter.api.Test
A anotação @Test.
class ContaTest
A classe de testes. Não precisa ser public, e não tem main: quem a executa é o JUnit.
@Test
Uma anotação: uma etiqueta que diz ao JUnit "este método é um teste, rode-o". Sem ela, o método é ignorado.
void depositoAumentaOSaldo()
Um método de teste: void, sem parâmetros. O nome descreve o que está sendo conferido; ele aparece nos relatórios quando o teste falha.
Conta conta = new Conta("Ana");
Prepara o cenário.
conta.depositar(100.0);
Executa a ação testada.
assertEquals(100.0, conta.getSaldo());
Verifica: "o saldo deve ser 100.0". Primeiro o valor esperado, depois o obtido. Se forem diferentes, o teste falha.

Esse formato em três passos (preparar, executar, verificar) é o padrão de quase todo teste. Em inglês é chamado de Arrange, Act, Assert.

4. Testar exceções: assertThrows

    @Test
    void saqueSemSaldo() {
        Conta conta = new Conta("Ana");
        IllegalStateException erro = assertThrows(IllegalStateException.class,
                () -> conta.sacar(500.0));
        assertEquals("Saldo insuficiente", erro.getMessage());
    }
assertThrows(
"Verifique que isto lança uma exceção." Importado como o assertEquals: import static org.junit.jupiter.api.Assertions.assertThrows;
IllegalStateException.class
Qual exceção é esperada. O .class se refere à classe da exceção em si (e não a um objeto dela).
() -> conta.sacar(500.0)
Uma lambda: um "pedaço de código guardado" que o assertThrows executa quando quiser. Leia como "a ação de sacar 500". Se você escrevesse só conta.sacar(500.0), a exceção estouraria antes de o assertThrows começar.
IllegalStateException erro = …
O assertThrows devolve a exceção capturada, para você conferir a mensagem.

Se o código não lançar a exceção, o teste falha com: Expected java.lang.IllegalStateException to be thrown, but nothing was thrown. (você vai ver essa mensagem real na seção de testes parametrizados).

5. Preparar cada teste: @BeforeEach

Todo teste da Conta começa com new Conta("Ana") e, muitas vezes, um depósito inicial. Repetir isso em cada método é cansativo. Um método marcado com @BeforeEach ("antes de cada") roda antes de cada teste, preparando o cenário:

    private Conta conta;

    @BeforeEach
    void criarConta() {
        conta = new Conta("Ana");
        conta.depositar(100.0);
    }

    @Test
    void saqueDiminuiOSaldo() {
        conta.sacar(30.0);
        assertEquals(70.0, conta.getSaldo());
    }

Importante: o JUnit cria um objeto novo de ContaTest para cada teste, e roda o @BeforeEach de novo. Assim, cada teste começa com uma conta nova de saldo 100, sem sobras do teste anterior. Testes nunca devem depender da ordem em que rodam.

AnotaçãoQuando rodaUso típico
@BeforeEachAntes de cada testeCriar os objetos do cenário
@AfterEachDepois de cada testeApagar arquivos temporários
@BeforeAllUma vez, antes de todos (método static)Algo caro, feito uma vez só
@AfterAllUma vez, depois de todos (static)Liberar o que o @BeforeAll criou

7. Testes parametrizados: um teste, vários valores

Para conferir que depósitos de 0, -1 e -50 são todos recusados, você escreveria três testes quase iguais. Um teste parametrizado recebe os valores como parâmetro e roda uma vez para cada um:

    @ParameterizedTest
    @ValueSource(doubles = {0.0, -1.0, -50.0})
    @DisplayName("depósito zero ou negativo é recusado")
    void depositoInvalido(double valor) {
        assertThrows(IllegalArgumentException.class, () -> conta.depositar(valor));
    }

    @ParameterizedTest
    @CsvSource({"10.0, 90.0", "100.0, 0.0", "0.5, 99.5"})
    void saquesValidos(double saque, double saldoEsperado) {
        conta.sacar(saque);
        assertEquals(saldoEsperado, conta.getSaldo());
    }
@ParameterizedTest
No lugar de @Test: "teste com parâmetros".
@ValueSource(doubles = {…})
A fonte dos valores: uma lista de double (há também ints, strings…). Cada valor vira uma execução, com o valor no parâmetro valor.
@CsvSource({"10.0, 90.0", …})
Para vários parâmetros por execução: cada texto é uma linha "separada por vírgulas" (CSV). "10.0, 90.0" = sacar 10, saldo esperado 90.

A classe de testes completa

package br.com.ana.banco;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;

@DisplayName("Conta da Ana")
class ContaTest {

    private Conta conta;

    @BeforeEach
    void criarConta() {
        conta = new Conta("Ana");
        conta.depositar(100.0);
    }

    @Test
    @DisplayName("depósito aumenta o saldo")
    void depositoAumentaOSaldo() {
        conta.depositar(50.0);
        assertEquals(150.0, conta.getSaldo());
    }

    @Test
    @DisplayName("saque diminui o saldo")
    void saqueDiminuiOSaldo() {
        conta.sacar(30.0);
        assertEquals(70.0, conta.getSaldo());
    }

    @Test
    @DisplayName("saque maior que o saldo é recusado")
    void saqueSemSaldo() {
        IllegalStateException erro = assertThrows(IllegalStateException.class,
                () -> conta.sacar(500.0));
        assertEquals("Saldo insuficiente", erro.getMessage());
        assertEquals(100.0, conta.getSaldo());
    }

    @ParameterizedTest
    @ValueSource(doubles = {0.0, -1.0, -50.0})
    @DisplayName("depósito zero ou negativo é recusado")
    void depositoInvalido(double valor) {
        assertThrows(IllegalArgumentException.class, () -> conta.depositar(valor));
    }

    @ParameterizedTest
    @CsvSource({"10.0, 90.0", "100.0, 0.0", "0.5, 99.5"})
    void saquesValidos(double saque, double saldoEsperado) {
        conta.sacar(saque);
        assertEquals(saldoEsperado, conta.getSaldo());
    }
}

8. As verificações mais usadas

MétodoPassa quando…
assertEquals(esperado, obtido)os dois são iguais (com equals para objetos)
assertEquals(0.3, x, 0.0001)o double x está a no máximo 0.0001 de 0.3 (para contas com casas decimais, que raramente dão exato; veja double e float)
assertNotEquals(a, b)são diferentes
assertTrue(condição) / assertFalse(condição)a condição é true / false
assertNull(x) / assertNotNull(x)x é / não é null
assertThrows(Tipo.class, () -> …)o código lança aquela exceção
assertDoesNotThrow(() -> …)o código não lança nada
assertAll(() -> …, () -> …)todas as verificações passam (e mostra todas as que falharam, não só a primeira)
fail("mensagem")nunca: falha na hora

Todas aceitam uma mensagem extra no fim, mostrada quando falham: assertEquals(150.0, saldo, "saldo depois de dois depósitos").

9. A ideia do TDD

TDD (Test-Driven Development, "desenvolvimento guiado por testes") é um jeito de trabalhar em que o teste vem antes do código. É um ciclo curto, de três passos, com nomes de cores:

  1. Vermelho: escreva um teste para algo que ainda não existe (por exemplo, "transferir 30 da conta da Ana para a do Bruno"). Rode: ele falha (nem compila, ou dá FAILURE).
  2. Verde: escreva o mínimo de código para o teste passar.
  3. Refatorar: com o teste verde protegendo, melhore o código (nomes, repetições) sem mudar o comportamento. Rode de novo.

A vantagem: você pensa primeiro em como a classe vai ser usada, e termina com todo o código coberto por testes. Não é obrigatório; muita gente escreve o teste logo depois do código. O importante é que o teste exista.

Resumo

  • Testes automatizados conferem o programa sozinhos, em segundos, a cada mudança, e pegam regressões.
  • No Maven: dependência org.junit.jupiter:junit-jupiter com <scope>test</scope>; testes em src/test/java, classes terminadas em Test.
  • Um teste: @Test + preparar, executar, verificar. assertEquals(esperado, obtido).
  • mvn test: Tests run / Failures / Errors / Skipped. Failure = verificação errada; Error = exceção inesperada. Teste falhando = BUILD FAILURE.
  • assertThrows(Tipo.class, () -> …) testa exceções; @BeforeEach prepara cada teste; @DisplayName dá nomes legíveis.
  • @ParameterizedTest com @ValueSource ou @CsvSource roda o mesmo teste com vários valores.
  • TDD: vermelho (teste falha), verde (código mínimo), refatorar.
