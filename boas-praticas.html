Java Boas Práticas

Um programa pode funcionar hoje e ser um pesadelo amanhã: difícil de ler, fácil de quebrar, com defeitos escondidos. As boas práticas são hábitos que programadores experientes aprenderam (muitas vezes do jeito difícil) para escrever código claro e seguro. Esta aula reúne as mais importantes num checklist, cada uma com o porquê e um exemplo real, e termina com uma refatoração completa, passo a passo.

Você vai aprender
  • 12 regras práticas, com o defeito real que cada uma evita.
  • Como transformar um código "que funciona mais ou menos" num código limpo, uma mudança por vez.
  • Onde estão as convenções oficiais de formatação (Oracle e Google).

Esta aula é uma revisão: cada item aponta para a aula onde o assunto foi explicado em detalhe. Use-a como lista de conferência antes de considerar um programa "pronto".

A ideia: o checklist do piloto

Antes de decolar, até o piloto mais experiente percorre um checklist: combustível, flapes, instrumentos. Não é falta de conhecimento; é que, com pressa ou cansaço, qualquer um esquece algo óbvio. Boas práticas de programação funcionam igual: são lembretes simples que evitam os erros mais comuns. E têm um efeito extra: código escrito com os mesmos hábitos é mais fácil para outras pessoas lerem. Lembre-se: o código é lido muito mais vezes do que é escrito.

1. Nomes que dizem o que a coisa é

O nome é a primeira documentação. Compare:

double calc(ArrayList<String> x, String c) {
    double t = 0;

BigDecimal totalDoCliente(List<Venda> vendas, String cliente) {
    BigDecimal total = BigDecimal.ZERO;

No primeiro, você precisa ler o método inteiro para adivinhar o que é x, c e t. No segundo, a assinatura já conta a história. As convenções de Java para nomes:

O quêEstiloExemplo
Classes, interfaces, records, enumsPascalCase (substantivo)Conta, ItemDoPedido
MétodoscamelCase (verbo)depositar, calcularFrete, isVazio
Variáveis e atributoscamelCasesaldo, totalDoCliente
Constantes (static final)MAIUSCULAS_COM_SUBLINHADOTAXA_DE_ENTREGA

Nomes de uma letra só são aceitáveis em laços muito curtos (i) e lambdas pequenas (x -> x * 2). Português ou inglês? Os dois funcionam; o importante é não misturar no mesmo projeto (veja Variáveis e Sintaxe).

2. Métodos curtos, que fazem uma coisa só

Se você precisa de "e" para descrever o que um método faz ("lê o arquivo e calcula o total e imprime o relatório"), ele está fazendo coisas demais. Divida em métodos menores, cada um com um nome que explica o passo (veja Métodos). Vantagens: cada pedaço é fácil de entender, de testar com JUnit e de reaproveitar. Uma referência prática: se o método não cabe inteiro na tela, desconfie.

3. final e imutabilidade

Um valor que não muda é um valor em que você pode confiar: ninguém vai alterá-lo "pelas costas". Marque com final o que não deve mudar (veja final), e o compilador vigia por você:

public class Final {
    public static void main(String[] args) {
        final double taxa = 0.05;
        taxa = 0.10;
    }
}

$ java Final.java
Final.java:4: error: cannot assign a value to final variable taxa
        taxa = 0.10;
        ^
1 error
error: compilation failed

Para objetos, prefira classes imutáveis: atributos private final, sem set. Os records já nascem assim. E as listas criadas com List.of são imutáveis; tentar mudar dá erro na hora, em vez de um defeito silencioso depois:

$ java Imutavel.java
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:159)
	at java.base/java.util.ImmutableCollections$AbstractImmutableCollection.add(ImmutableCollections.java:164)
	at Imutavel.main(Imutavel.java:6)

(O Imutavel.java faz List.of("maçã", "banana") e depois frutas.add("uva").)

4. Não engula exceções

"Engolir" uma exceção é capturá-la e não fazer nada, com um catch vazio. O erro some, e o programa segue com um valor errado:

public class Engole {
    public static void main(String[] args) {
        int quantidade = 0;
        try {
            quantidade = Integer.parseInt("1O");
        } catch (NumberFormatException e) {
        }
        System.out.println("Quantidade: " + quantidade);
    }
}

$ java Engole.java
Quantidade: 0

Alguém digitou a letra O em vez do zero em "10". O programa não reclamou e registrou quantidade 0. Ninguém vai saber por quê. Regras:

  • Se você sabe tratar o erro (pedir de novo, usar um valor padrão que faça sentido), trate, e de preferência avise (uma mensagem ou um log).
  • Se não sabe, não capture: deixe a exceção subir (veja throw e throws). Um programa que para com uma mensagem clara é melhor que um que segue errado.
  • Capture o tipo específico (NumberFormatException), não Exception: assim você não esconde, sem querer, defeitos de outro tipo.

5. equals e hashCode sempre juntos

Quem sobrescreve equals (veja A Classe Object) tem de sobrescrever hashCode também. Senão, as coleções que usam hash, como HashSet e HashMap, se comportam de forma absurda:

import java.util.HashSet;
import java.util.Set;

public class Produto {
    private final String codigo;

    Produto(String codigo) {
        this.codigo = codigo;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Produto p && codigo.equals(p.codigo);
    }

    public static void main(String[] args) {
        Produto a = new Produto("CAFE-500");
        Produto b = new Produto("CAFE-500");
        System.out.println(a.equals(b));
        Set<Produto> estoque = new HashSet<>();
        estoque.add(a);
        estoque.add(b);
        System.out.println(estoque.size());
        System.out.println(estoque.contains(new Produto("CAFE-500")));
    }
}

$ java Produto.java
true                « a e b são iguais pelo equals…
2                   « …mas o conjunto (que não aceita repetidos) guardou os dois
false               « e diz que não contém um produto igual

O HashSet primeiro usa o hashCode para escolher a "gaveta" do objeto, e só depois compara com equals dentro da gaveta. Sem hashCode próprio, objetos iguais caem em gavetas diferentes. Acrescentando, na mesma classe (no laboratório, numa cópia chamada Produto2):

    @Override
    public int hashCode() {
        return codigo.hashCode();
    }

$ java Produto2.java
true
1
true

Regra: os campos usados no equals são os mesmos do hashCode (com vários campos, use Objects.hash(campo1, campo2)). Melhor ainda: se a classe é só um "pacote de dados", use um record, que gera os dois corretamente sozinho. Veja também HashSet.

6. Use interfaces nos tipos

ArrayList<String> nomes = new ArrayList<>();
static double calc(ArrayList<String> x) { … }

List<String> nomes = new ArrayList<>();
static BigDecimal total(List<Venda> vendas) { … }

Declare variáveis, parâmetros e retornos com a interface (List, Set, Map) e use a classe concreta só no new. Assim, o método aceita qualquer lista (ArrayList, LinkedList, List.of…), e trocar a implementação depois exige mudar uma linha só. É o polimorfismo trabalhando a seu favor (veja Visão Geral das Coleções).

7. Devolva coleção vazia, não null

Um método que devolve uma lista não deveria devolver null quando "não tem nada". Quem chama quase sempre esquece de conferir:

import java.util.List;

public class Nulos {
    static List<String> pedidosDe(String cliente) {
        if (cliente.equals("Bruno")) {
            return List.of("café", "pão");
        }
        return null;
    }

    public static void main(String[] args) {
        for (String p : pedidosDe("Bruno")) {
            System.out.println("Bruno: " + p);
        }
        for (String p : pedidosDe("Carla")) {
            System.out.println("Carla: " + p);
        }
    }
}

$ java Nulos.java
Bruno: café
Bruno: pão
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.util.List.iterator()" because the return value of "Nulos.pedidosDe(String)" is null
	at Nulos.main(Nulos.java:15)

Com return List.of(); (uma lista vazia) no lugar do return null;, o for da Carla simplesmente não roda nenhuma vez, e o programa segue. Vale o mesmo para arrays (new String[0]), mapas (Map.of()) e textos ("", quando fizer sentido).

8. Optional só como retorno

Para um método que busca um valor que pode não existir, o retorno Optional obriga quem chama a pensar no caso "não achou":

Optional<Conta> buscarPorTitular(String titular) { … }

buscarPorTitular("Carla")
        .ifPresentOrElse(c -> System.out.println(c.getSaldo()),
                         () -> System.out.println("Conta não encontrada"));

Mas Optional foi feito para isso: retorno de método. Evite usá-lo como atributo de classe, como parâmetro (void enviar(Optional<String> obs) obriga quem chama a embrulhar o valor; prefira dois métodos, ou aceitar null e documentar) e dentro de coleções (List<Optional<…>>: simplesmente não ponha os vazios na lista). E nunca chame .get() sem saber se há valor: é trocar um NullPointerException por um NoSuchElementException.

9. try-with-resources para tudo que precisa ser fechado

Arquivos, conexões e Scanners de arquivo ocupam recursos do sistema e precisam ser fechados, mesmo se der erro no meio. Em vez de lembrar de chamar close() num finally, declare o recurso entre parênteses no try e o Java fecha sozinho (veja finally e try-with-resources):

try (BufferedWriter saida = Files.newBufferedWriter(Path.of("vendas.txt"))) {
    saida.write("Ana;café;10.90");
    saida.newLine();
}   // aqui o arquivo já foi fechado, com ou sem exceção

10. Compare Strings com equals, nunca com ==

O == compara se são o mesmo objeto, não se têm o mesmo texto (veja Strings e Operadores de Comparação). O perigo: às vezes ele "funciona", e você acha que está certo:

public class Strings {
    public static void main(String[] args) {
        String a = "Ana";
        String b = "Ana";
        String c = new StringBuilder("An").append("a").toString();
        System.out.println(a == b);
        System.out.println(a == c);
        System.out.println(a.equals(c));
    }
}

$ java Strings.java
true                « dois textos escritos no código: o Java reaproveita o mesmo objeto
false               « o mesmo texto, montado durante a execução: outro objeto
true                « equals compara o conteúdo: sempre certo

Textos que vêm do teclado, de arquivos ou de split são montados durante a execução, como o c. Por isso o == funciona nos seus testes rápidos (com textos escritos no código) e falha com dados de verdade. Use equals (ou equalsIgnoreCase). Com uma constante, escreva-a primeiro, "Ana".equals(nome), que funciona mesmo se nome for null.

Missão: o nome vem de um split, como se tivesse sido lido de um cadastro. Rode e veja que o == diz que não é a Ana. Corrija a comparação para aparecer Bem-vinda, Ana!.

public class Main {
    public static void main(String[] args) {
        String nome = "Ana Souza".split(" ")[0];
        if (nome == "Ana") {
            System.out.println("Bem-vinda, Ana!");
        } else {
            System.out.println("Quem é você, " + nome + "?");
        }
    }
}

public class Main {
    public static void main(String[] args) {
        String nome = "Ana Souza".split(" ")[0];
        if (nome.equals("Ana")) {
            System.out.println("Bem-vinda, Ana!");
        } else {
            System.out.println("Quem é você, " + nome + "?");
        }
    }
}

(No laboratório, a versão com == mostrou Quem é você, Ana?: o texto é "Ana", mas não é o mesmo objeto.)

11. BigDecimal para dinheiro

double guarda números em binário e não consegue representar exatamente valores como 0,1 (veja double e float). Para medir distâncias, tudo bem; para dinheiro, os centavos "fantasmas" viram problema:

import java.math.BigDecimal;

public class Dinheiro {
    public static void main(String[] args) {
        System.out.println(0.1 + 0.2);
        System.out.println(1.10 - 1.00);
        BigDecimal x = new BigDecimal("0.1").add(new BigDecimal("0.2"));
        System.out.println(x);
        System.out.println(new BigDecimal("1.10").subtract(new BigDecimal("1.00")));
        System.out.println(new BigDecimal(0.1));
    }
}

$ java Dinheiro.java
0.30000000000000004
0.10000000000000009
0.3
0.10
0.1000000000000000055511151231257827021181583404541015625

Com BigDecimal criado a partir de texto (new BigDecimal("0.1")), as contas são exatas. A última linha mostra a armadilha: new BigDecimal(0.1), com o double, herda o erro do double. Use sempre a versão com aspas (ou BigDecimal.valueOf(0.1)).

Missão: a Ana comprou café (R$ 10,90) e leite (R$ 4,20). Com double, o total sai 15.100000000000001. Reescreva com BigDecimal (criado a partir de texto) para mostrar Total: 15.10.

public class Main {
    public static void main(String[] args) {
        double cafe = 10.90;
        double leite = 4.20;
        double total = cafe + leite;
        System.out.println("Total: " + total);
    }
}

import java.math.BigDecimal;

public class Main {
    public static void main(String[] args) {
        BigDecimal cafe = new BigDecimal("10.90");
        BigDecimal leite = new BigDecimal("4.20");
        BigDecimal total = cafe.add(leite);
        System.out.println("Total: " + total);
    }
}

12. Formate o código (e deixe a ferramenta fazer isso)

Recuo, espaços e chaves não mudam o que o programa faz, mas mudam muito o quanto ele é fácil de ler. O importante é que todo o projeto siga o mesmo padrão. Os dois mais conhecidos:

Convenções da Oracle (Code Conventions for the Java Programming Language)Google Java Style Guide
Recuo4 espaços2 espaços
Tamanho da linha80 caracteres100 caracteres
Chave {No fim da linhaNo fim da linha
if de uma linhaSempre com chavesSempre com chaves
Um comando por linhaSimSim

Este guia usa 4 espaços e chaves no fim da linha, o mais comum. Não formate à mão: toda IDE formata o arquivo inteiro com um atalho (IntelliJ: Ctrl+Alt+L; VS Code: Shift+Alt+F no Linux e Windows). Em equipes, ferramentas como o google-java-format e o Checkstyle conferem o padrão automaticamente no build. Veja também Sintaxe e Estrutura.

Antes × depois: uma refatoração completa

Refatorar é melhorar a estrutura do código sem mudar o que ele deveria fazer. A Ana encontrou este código antigo, que soma as compras de um cliente a partir de linhas no formato cliente;produto;valor:

Este código tem defeitos de propósito
import java.util.*;

public class Antes {
    static ArrayList<String> v = new ArrayList<>();

    static double calc(ArrayList<String> x, String c) {
        double t = 0;
        try {
            for (int i = 0; i < x.size(); i++) {
                String[] p = x.get(i).split(";");
                if (p[0] == c) {
                    t = t + Double.parseDouble(p[2]);
                }
            }
        } catch (Exception e) {
        }
        return t;
    }

    public static void main(String[] args) {
        v.add("Ana;café;10.90");
        v.add("Bruno;pão;0.80");
        v.add("Ana;leite;4.20");
        v.add("Ana;açúcar;x");
        System.out.println("Total da Ana: " + calc(v, "Ana"));
    }
}

$ java Antes.java
Total da Ana: 0.0

A Ana comprou R$ 15,10, e o programa diz zero. Corrigindo só o == (item 10) para p[0].equals(c):

$ java Antes2.java
Total da Ana: 15.100000000000001

Melhorou, mas apareceram os centavos fantasmas do double, e a linha Ana;açúcar;x (com valor inválido) sumiu sem aviso, engolida pelo catch vazio. Pior: como o try envolve o laço inteiro, se essa linha estivesse no meio da lista, todas as seguintes também seriam ignoradas. A versão refatorada:

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class Depois {

    record Venda(String cliente, String produto, BigDecimal valor) {
        static Venda ler(String linha) {
            String[] partes = linha.split(";");
            return new Venda(partes[0], partes[1], new BigDecimal(partes[2]));
        }
    }

    static List<Venda> lerVendas(List<String> linhas) {
        List<Venda> vendas = new ArrayList<>();
        for (String linha : linhas) {
            try {
                vendas.add(Venda.ler(linha));
            } catch (NumberFormatException e) {
                System.err.println("Linha ignorada (valor inválido): " + linha);
            }
        }
        return vendas;
    }

    static BigDecimal totalDoCliente(List<Venda> vendas, String cliente) {
        BigDecimal total = BigDecimal.ZERO;
        for (Venda venda : vendas) {
            if (venda.cliente().equals(cliente)) {
                total = total.add(venda.valor());
            }
        }
        return total;
    }

    public static void main(String[] args) {
        List<String> linhas = List.of(
                "Ana;café;10.90",
                "Bruno;pão;0.80",
                "Ana;leite;4.20",
                "Ana;açúcar;x");
        List<Venda> vendas = lerVendas(linhas);
        System.out.println("Total da Ana: " + totalDoCliente(vendas, "Ana"));
    }
}

$ java Depois.java
Linha ignorada (valor inválido): Ana;açúcar;x
Total da Ana: 15.10

Quando dá errado

"Funcionava nos meus testes, mas com dados reais não"

Suspeitos de sempre: == entre Strings (funciona com textos escritos no código, falha com textos lidos); double com dinheiro (os centavos aparecem só com alguns valores); catch vazio (o erro acontece só com certas entradas e some). Revise os itens 4, 10 e 11.

NullPointerException em lugares variados

O que aconteceu: algum método devolve null para dizer "nada". Como resolver: devolva coleções vazias (item 7) ou Optional (item 8); leia a mensagem do NullPointerException, que diz qual valor era null (because the return value of "Nulos.pedidosDe(String)" is null).

Objetos "iguais" duplicados num HashSet ou não encontrados num HashMap

O que aconteceu: equals sem hashCode (item 5), ou um objeto mutável que mudou depois de entrar na coleção. Como resolver: sobrescreva os dois com os mesmos campos, ou use um record.

Resumo

  • Nomes claros, métodos curtos com uma responsabilidade, e o que não muda marcado como final (ou records e List.of).
  • Nunca engula exceções: trate e avise, ou deixe subir. Capture tipos específicos.
  • equals e hashCode sempre juntos (ou record).
  • Interfaces nos tipos (List, Map); coleções vazias no lugar de null; Optional só como retorno.
  • try-with-resources para fechar recursos; equals para Strings; BigDecimal (de texto) para dinheiro.
  • Formate com a ferramenta, num padrão só (Oracle: 4 espaços; Google: 2).
  • Refatorar é melhorar a estrutura uma mudança por vez, conferindo a saída (ou os testes) a cada passo.
