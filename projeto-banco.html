Projeto Conta Bancária com Testes

Dinheiro não aceita "quase certo". Neste projeto você constrói uma conta bancária que deposita, saca e transfere com centavos exatos, recusa saques sem saldo com uma exceção própria e, o mais importante, vem com testes automáticos: pequenos programas que conferem a conta inteira com um único comando, mvn test. No fim, você vai quebrar o código de propósito e ver os testes pegarem o erro antes de qualquer cliente.

Você vai praticar
  • Montar um projeto Maven do zero, com o JUnit como dependência.
  • Representar dinheiro com BigDecimal (e entender por que não double).
  • Encapsulamento: o saldo só muda por depósito, saque e transferência.
  • Exceção própria checked: SaldoInsuficienteException.
  • Testes com JUnit 5: @Test, @BeforeEach, assertEquals, assertThrows.
  • Ler um relatório de teste que falhou e consertar o código.

Etapa 2 · A conta e o dinheiro exato

Por que não guardar o saldo num double? Porque o double guarda números em binário, e a maioria dos centavos não tem representação exata em binário (como 1/3 não tem em decimal). Veja no JShell:

$ jshell
|  Welcome to JShell -- Version 25.0.4.1
|  For an introduction type: /help intro

jshell> 0.1 + 0.2
$1 ==> 0.30000000000000004

jshell> new java.math.BigDecimal("0.1").add(new java.math.BigDecimal("0.2"))
$2 ==> 0.3

Para um jogo, 0.30000000000000004 não faz diferença. Para um banco, depois de milhões de operações, faz. O BigDecimal guarda o número em decimal, dígito por dígito, e as contas saem exatas. A Conta, por enquanto só com depósito:

package br.com.ana.banco;

import java.math.BigDecimal;

public class Conta {
    private final String titular;
    private BigDecimal saldo = BigDecimal.ZERO;

    public Conta(String titular) {
        this.titular = titular;
    }

    public String getTitular() {
        return titular;
    }

    public BigDecimal getSaldo() {
        return saldo;
    }

    public void depositar(BigDecimal valor) {
        validar(valor);
        saldo = saldo.add(valor);
    }

    private static void validar(BigDecimal valor) {
        if (valor == null || valor.signum() <= 0) {
            throw new IllegalArgumentException("O valor deve ser positivo: " + valor);
        }
    }
}
TrechoO que faz
package br.com.ana.banco;Primeira linha de todo arquivo do projeto: o pacote, igual às pastas.
BigDecimal.ZEROUma constante pronta com o valor 0.
saldo = saldo.add(valor);BigDecimal não usa +: usa métodos (add, subtract, multiply). E ele é imutável: add devolve um número novo, que precisa ser guardado de volta em saldo. Só escrever saldo.add(valor); não muda nada.
valor.signum() <= 0signum ("sinal") devolve -1, 0 ou 1. Recusamos zero e negativos.
private static void validarUm método auxiliar só da classe; o depósito e (logo mais) o saque usam o mesmo.
Sem setSaldoO saldo só muda por operações bancárias (encapsulamento).

Crie BigDecimal a partir de texto

new BigDecimal("0.1") é exatamente 0,1. Já new BigDecimal(0.1) recebe o double, que já nasceu errado, e mostra o erro todo: 0.1000000000000000055511151231257827021181583404541015625. Use sempre a versão com aspas (ou BigDecimal.valueOf(0.1)). Detalhes em BigDecimal e Dinheiro.

Etapa 3 · O primeiro teste

Até agora, para saber se a conta funciona, você roda o App e olha a saída. Um teste automático faz isso por você: ele chama a conta e confere o resultado, sem ninguém precisar olhar. O arquivo fica em src/test/java, no mesmo pacote:

package br.com.ana.banco;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import java.math.BigDecimal;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class ContaTest {
    private Conta ana;
    private Conta bruno;

    @BeforeEach
    void preparar() {
        ana = new Conta("Ana");
        bruno = new Conta("Bruno");
    }

    @Test
    void depositoAumentaOSaldo() {
        ana.depositar(new BigDecimal("100.50"));
        assertEquals(new BigDecimal("100.50"), ana.getSaldo());
    }

    @Test
    void centavosSomamSemErro() {
        ana.depositar(new BigDecimal("0.10"));
        ana.depositar(new BigDecimal("0.20"));
        assertEquals(new BigDecimal("0.30"), ana.getSaldo());
    }

    @Test
    void depositoNegativoEhRecusado() {
        assertThrows(IllegalArgumentException.class, () -> ana.depositar(new BigDecimal("-5.00")));
    }
}
import static …Assertions.assertEquals;
Um import static traz o método para usar sem o nome da classe: assertEquals(…) em vez de Assertions.assertEquals(…).
@BeforeEach void preparar()
Roda antes de cada teste: cada um começa com contas novas, zeradas, sem depender dos outros.
@Test
Marca um método como teste. O nome do método descreve o que se espera: depositoAumentaOSaldo.
assertEquals(esperado, obtido)
"Afirme que são iguais." Se não forem, o teste falha. Primeiro o esperado, depois o que o código produziu.
assertThrows(IllegalArgumentException.class, () -> …)
"Afirme que isto lança essa exceção." O () -> … é uma lambda: um pedaço de código que o JUnit roda dentro de uma proteção. Se a exceção não vier, o teste falha.

Etapa 4 · Saque e SaldoInsuficienteException

Sacar mais do que se tem não é um "erro de programação": é uma situação normal do banco, que quem chama o sacar precisa tratar (mostrar uma mensagem, oferecer um valor menor…). Por isso a exceção é checked (estende Exception):

package br.com.ana.banco;

import java.math.BigDecimal;

public class SaldoInsuficienteException extends Exception {
    public SaldoInsuficienteException(BigDecimal saldo, BigDecimal pedido) {
        super("Saldo insuficiente: saldo " + saldo + ", pedido " + pedido);
    }
}

E o método novo da Conta:

    public void sacar(BigDecimal valor) throws SaldoInsuficienteException {
        validar(valor);
        if (valor.compareTo(saldo) > 0) {
            throw new SaldoInsuficienteException(saldo, valor);
        }
        saldo = saldo.subtract(valor);
    }
throws SaldoInsuficienteException
Avisa que o saque pode falhar por falta de saldo. Quem chamar é obrigado a tratar ou repassar.
valor.compareTo(saldo) > 0
Com BigDecimal não se usa >. a.compareTo(b) devolve um número negativo (a menor), 0 (iguais) ou positivo (a maior). "> 0" = o valor pedido é maior que o saldo.
throw new SaldoInsuficienteException(saldo, valor)
Lança antes de mexer no saldo: se falhar, a conta fica como estava.
saldo.subtract(valor)
Subtração, de novo guardando o resultado.

Dois testes novos no ContaTest:

    @Test
    void saqueDiminuiOSaldo() throws SaldoInsuficienteException {
        ana.depositar(new BigDecimal("100.00"));
        ana.sacar(new BigDecimal("30.25"));
        assertEquals(new BigDecimal("69.75"), ana.getSaldo());
    }

    @Test
    void saqueMaiorQueOSaldoLancaExcecao() {
        ana.depositar(new BigDecimal("50.00"));
        SaldoInsuficienteException erro = assertThrows(SaldoInsuficienteException.class,
                () -> ana.sacar(new BigDecimal("80.00")));
        assertEquals("Saldo insuficiente: saldo 50.00, pedido 80.00", erro.getMessage());
        assertEquals(new BigDecimal("50.00"), ana.getSaldo());
    }

O primeiro teste tem throws SaldoInsuficienteException porque chama sacar sem try; se a exceção vier, o JUnit marca o teste como erro. O segundo confere três coisas: que a exceção veio, que a mensagem está certa e que o saldo não mudou.

Missão (etapa 4): o método sacar está vazio: o saldo nunca muda. Escreva-o: valide o valor, lance SaldoInsuficienteException se o valor for maior que o saldo (use compareTo) e subtraia com subtract.

import java.math.BigDecimal;

public class Main {
    public static void main(String[] args) {
        Conta ana = new Conta("Ana");
        ana.depositar(new BigDecimal("100.00"));
        try {
            ana.sacar(new BigDecimal("30.25"));
            System.out.println("Saldo: " + ana.getSaldo());
            ana.sacar(new BigDecimal("80.00"));
            System.out.println("Saldo: " + ana.getSaldo());
        } catch (SaldoInsuficienteException e) {
            System.out.println("Erro: " + e.getMessage());
        }
    }

Etapa 5 · Transferência

Transferir é sacar de uma conta e depositar na outra. Como os dois métodos já existem e já têm as regras, a transferência fica com duas linhas:
